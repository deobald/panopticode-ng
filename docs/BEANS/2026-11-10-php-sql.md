# PHP SQL inspection and repeatable repository health reports

Status: Proposed; not implemented.

## Objective

Create a native PHP `php-sql/` sub-project of `panopticode-ng` that discovers
database call sites, captures realistic executed SQL, examines database plans
and workload evidence, and reports inefficient queries and potential index
improvements with source locations and explicit confidence/coverage limits.

The first targets are the sibling `prosim-course-node` and
`prosim-management-node` repositories. They are PHP applications despite their
names. The package should support other PHP applications through adapters,
and its evidence formats should allow future TypeScript or C# collectors.

## Initial repository evidence

- Both applications use CodeIgniter 4.3.0 and have SQL scattered across
  controllers, models and helpers, including dynamic strings and query builders.
- Their local Docker configurations use MySQL 8.0. Deployed databases use RDS;
  the actual engine, version and topology still need confirmation. RDS alone
  does not establish MySQL versus Aurora MySQL or the available plan features.
- CodeIgniter's installed database layer emits `DBQuery` events with the
  original/resolved query, connection and execution timing available.
- Both applications use `getDBReader()` / `getDBWriter()` helpers. A reader
  request can return the writer after related tables become dirty, so record
  the actual connection and schema rather than inferring them from helper names.
- Existing database tests provide useful starting scenarios, but default test
  configuration uses SQLite. SQLite execution and small test fixtures cannot
  establish representative MySQL plans or performance.
- Management pilot candidates include school search in
  `app/Controllers/Admin.php` (leading-wildcard search and per-school queries)
  and purchase reporting in `app/Controllers/Backend.php` (date predicates
  using `MONTH()` / `YEAR()`). These are investigation candidates, not verified
  performance defects or confirmed missing indexes.

## Architecture and evidence

Keep `php-sql/` separate from the existing `php/` code-health analyzer, with its
own dependencies, lockfiles, configuration, tests and documentation. Provide:

1. **Source inventory:** Find database call sites, wrappers, literal SQL,
   string construction, query-builder usage and queries inside loops. Resolve
   expressions where possible and retain unresolved dynamic fragments. Do not
   pretend static extraction can reconstruct every executable SQL variant.
2. **Capture adapters:** Start with a small, independently loadable CodeIgniter
   collector. Applications should not need the full inspector installed to
   produce captures. Observe final SQL at the database boundary, and retain
   original SQL, application call stacks, request/test/scenario identifiers,
   query order, duration, success/failure, and actual connection/schema identity.
   Capture typed parameter information where available. Audit direct driver
   calls and other framework bypasses and add adapters or expose those gaps.
3. **Workload import:** Accept saved captures and database-side observations
   that establish real query frequency and cost. Account for stored procedures
   and other SQL invisible to application-level capture. Preserve unmatched
   database-observed query shapes as evidence gaps.
4. **Database adapters:** Collect schema/index metadata, relevant settings and
   statistics, and plans using the confirmed target engine's supported features.
   For MySQL-compatible targets, use structured estimated plans and selectively
   collect actual execution plans. Record parameter samples and database context.
5. **Reconciliation and reporting:** Connect source call sites, concrete query
   variants, exercised scenarios, workload observations and examined plans.
   Produce offline HTML and versioned JSON, with raw evidence available for
   inspection. Keep measurements separate from findings and recommendations.

Collect application traces first and examine them in a separate process; do not
run plan analysis recursively inside a query event handler. Retain execution
samples privately when needed for planning, and redact sensitive values from
shareable reports. Avoid collecting connection credentials or backtrace arguments.

## Realistic extraction and coverage

Instrument the shared database boundary so scattered SQL does not require a
centralized query layer or manual copying. Use source inspection to identify
what runtime scenarios have not reached, and observed database workload to
identify what the scenario suite has missed.

Group equivalent query shapes, but preserve representative parameter cases and
generated variants: small/large schools or courses, short/long lists, empty and
populated results, optional filters, sorting, pagination, reporting periods,
and connection routing. Use representative database fixtures or snapshots,
including important cardinalities and skew. Do not substitute arbitrary
placeholder values when claiming a representative plan.

Preserve each request's query sequence and repetition counts. A query that is
fast once can still dominate a workflow when repeated for every result row.
Deduplication must not hide N+1 patterns or cumulative database time.

Maintain a coverage ledger:

```text
Source call site -> exercised scenario -> observed SQL variants
                 -> connection/schema -> workload evidence -> examined plans
```

Show observed/examined, observed/unexamined, unresolved and unexercised states
explicitly. Report source-inventory limitations and capture bypasses. Never
claim that observing some scenarios proves every possible query was examined.

## Repository health orchestration

The eventual orchestration project belongs at `~/work/health/`, beside
`panopticode-ng` and its target repositories. It should register each repository's
applicable analyzers, checkout, exclusions, test/scenario commands, database
fixtures and evidence inputs, and produce separate reports for every repository.
Creating this bean does not authorize creating or changing that sibling project.

Illustrative structure:

```text
~/work/health/
  configuration/
  scenarios/
  evidence/<repo>/
  reports/index.html
  reports/<repo>/report.html
```

Separate these operations; names below describe proposed interfaces, not
implemented commands or a settled CLI contract:

| Operation | Behavior | Expected manual work |
| --- | --- | --- |
| `health build [REPO]` | Render saved evidence for one/all repositories without live collection. | None. |
| `health refresh REPO` | Run configured checks/scenarios, capture fresh evidence and plans, then rebuild that repository's report. | Normally none after setup. |
| `health experiment REPO EXPERIMENT` | Execute a specified comparison on disposable database copies and save comparison evidence. | Initially select the candidate and define its comparison. |

A refresh runs configured integrated passes by default, with explicit opt-outs
and visible failed/skipped/unavailable states. An offline build renders the
supplied evidence; it does not silently refresh or treat old evidence as current.
Identify source revisions and stale/incompatible evidence explicitly.

## Determinism and provenance

- Identical saved evidence and renderer versions should produce identical report
  bytes. Use canonical ordering, portable source paths and stable identifiers.
  Keep variable collection timestamps/run identifiers outside canonical results
  or supply them as explicit inputs. Do not inject the rebuild time into reports.
- Make fresh evidence collection reproducible by recording/pinning source
  revisions, tool and adapter versions, configuration, scenario inputs/seeds,
  database fixture identity, engine version, schema/index definitions and
  relevant optimizer settings/statistics. Record the scope of workload sampling.
- Distinguish stable assertions, such as query counts and result equivalence,
  from variable measurements. Fresh timings cannot be perfectly deterministic:
  caches, concurrency, scheduling and RDS conditions introduce variation.
  Define repetition and cache protocols and report variation. Plan comparisons
  must account for changes in data, statistics and optimizer versions.
- Preserve failed, partial, missing and stale evidence; never turn these into a
  successful zero findings result. Do not create an aggregate health score.

## Index and query experiments

Ordinary inspection measures the existing database and proposes candidates.
Index experiments deliberately change a disposable database copy and are a
separate, explicitly invoked operation. Rebuilding reports must not create or
remove indexes. Live database execution must have a configured target; actual
execution plans execute queries, and application scenarios can perform writes.
Use an isolated, resettable environment for scenario replay and experiments.

An experiment specification should identify:

- Baseline source revision, database fixture and schema.
- Candidate index migration or query rewrite.
- Scenarios and representative parameter cases.
- Result-equivalence expectations, including ordering and write effects where
  applicable; query-count and plan checks; and timing measurement protocol.
- Other relevant queries to check for regressions and the index's storage/write
  costs, rather than evaluating only the query that motivated it.

After the specification exists, the runner should restore equivalent baselines,
measure the baseline, apply the candidate to an equivalent disposable copy,
repeat the workload and produce comparison evidence without manual SQL copying,
database reset, index creation or result transcription. Promoting a successful
candidate into application/schema changes and deploying it remain separate work.

Full scans, filesorts, temporary tables and apparently unused indexes are review
signals, not automatic defects. Index recommendations must consider existing
indexes, selectivity, column order, data distribution and the wider workload.

## Tool candidates and first milestone

Consider `nikic/PHP-Parser` for source inventory, CodeIgniter's `DBQuery` event
for capture, and native database plan/metadata facilities. For MySQL-compatible
targets, Performance Schema / `sys` observations and optional Percona
`pt-query-digest` imports can complement application traces. A duplicate-index
checker may supply additional review evidence. Confirm concrete dependencies,
licenses, versions and engine compatibility before integration; this bean does
not approve an automatic schema-changing advisor.

First deliver a complete management school-search slice: source inventory,
CodeIgniter capture, repeatable MySQL scenarios, source-to-query reconciliation,
plan evidence and an offline report. Reuse the collector for course, then expand
to reporting and workload imports. Add experiments after collection and offline
rebuilding are reliable.

Acceptance should demonstrate deterministic rebuilds from a saved fixture,
correct source/connection attribution, multiple dynamic variants, N+1 detection,
unexercised-site reporting, explicit stale/missing/failed evidence, and a scripted
refresh that needs no manual query extraction. Later, demonstrate a repeatable
baseline/candidate experiment with result and workload regression checks.

Manual setup initially includes repository registration, establishing database
fixtures and isolated execution settings, installing the collector, and defining
representative scenarios. Reusable prompts and manually initiated agentic work
may eventually contribute additional rules/scenarios/evidence, but that workflow
is explicitly deferred for now.
